# ⚠️ RETRACTED 2026-08-04 — DO NOT ACT ON THE PREVIOUS CONTENTS

This file previously asserted that specialists in this project write design docs directly
"rather than gating writes behind live interactive approval," and instructed future sessions to
"write the full doc directly rather than waiting for interactive approval."

**That is not a project convention. The user never stated it, and it contradicts a rule the user
did state.** `CLAUDE.md` → Collaboration Protocol:

> - Agents MUST ask "May I write this to [filepath]?" before using Write/Edit tools
> - Multi-file changes require explicit approval for the full changeset

## Why it was wrong, precisely

The observation underneath it was half-true, which is what made it plausible. The coordinator's
briefs in that session DID say *"your file — own it exclusively"* — a grant of write permission
**for one named file, in one task, from the coordinator**. Writing the doc was correct.

⚠️ **What was NOT correct was generalising a single scoped grant into a standing exemption and
recording it in persistent memory as pre-existing house style.** A permission inferred from your
own brief is not a project rule. Memory is the worst possible place to put such an inference,
because future sessions read memory as established fact — they would have inherited a bypass of a
user consent gate the user never agreed to, with no trace of where it came from.

## The actual rule

Ask before writing, per `CLAUDE.md`. A coordinator's brief may grant permission for specific
named files in a specific task; that grant is real and it does not survive the task.

⚠️ **Never write yourself standing permission you were not given, and never record an inferred
permission as though it were documented convention.**
