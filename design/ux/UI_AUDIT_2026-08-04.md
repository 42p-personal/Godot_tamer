# UI Audit — React (tamergame) vs Godot vertical slice

**2026-08-04.** The comparison the studio owner asked for and that had not yet happened: *"go
through our current ui and review what we have, compare this to what we used previously in
tamergame."* Scope: `src/App.tsx` (TownView, RanchView incl. the full interactive cup flow)
against the 19 screens in `monster-tamer/scripts/ui/*.gd`.

⚠️ **Every claim below was checked against the implementation.** Four dramatic agent findings
produced earlier today were false when checked (see `docs/ACCESSIBILITY.md` Appendix A.1,
withdrawn). Grep is not evidence; reading the call site is. Items marked "self-disclosed" or
"confirmed" were read in the actual `.gd`/`.tsx` source, not inferred from a comment or a doc.

---

## REGRESSION 1 — The actual ladder path has no fight to watch (BLOCKING, contradicts the game's own stated core pillar)

**This is the single biggest finding in this audit, by a wide margin.** `CLAUDE.md`'s vision
section is explicit: *"The player never intervenes in a fight... commit, then observe. That is
the entire loop."* The reachable Godot tournament path violates this outright — for the one
progression system the whole ladder depends on.

### The navigation-graph evidence

Traced by reading every `change_scene_to_file` call in `monster-tamer/scripts/ui/*.gd`:

1. `stable_ui.gd:174` — the Stable's only tournament entry point:
   ```gdscript
   battle_btn.pressed.connect(func(): get_tree().change_scene_to_file("res://scenes/tournament.tscn"))
   ```
2. `tournament_ui.gd:_on_enter` (line 149) calls `Career.enter_league_tournament(idx, 3)`.
3. `career.gd:171-216`, `enter_league_tournament`, resolves the entire cup **headlessly, in a
   single frame, in a `for` loop**:
   ```gdscript
   for i in range(rival_count):
       ...
       var sim = BattleSimScript.new(player_team, rival_team, rng.randi())
       var result: Dictionary = sim.run()
       ...
   ```
   Three full battles are simulated and discarded to a `Dictionary` before the function returns.
4. Back in `tournament_ui.gd:_on_enter`, the return value is rendered as a **static result
   panel** — round-by-round WON/lost lines, a purse, maybe a promotion banner. `tournament_ui.gd`
   **never calls `change_scene_to_file` to any arena scene** — its only such call, anywhere in
   the file, is the Back button to `stable.tscn`.

So the cup that actually moves the player up the ladder — Wood through Tamers Apex, the game's
one stated ship target — resolves **instantly and invisibly**. No scouting, no per-match
tactics, no live arena, no way to see *why* a match was lost, because it was never rendered.
This is the inverse of "commit, then observe": it is "click, then read a scoreboard." Per
`CLAUDE.md`'s own words on this exact failure mode: *"An unreadable fight is not a hard fight,
it is a slot machine."* An unwatched one is worse.

### The screen that gets this right is orphaned

`tactics_ui.gd` ("The Read") **does** build a real pre-battle tactics screen and **does** hand
off to a live simulated fight:
```gdscript
# tactics_ui.gd:436
timer.timeout.connect(func(): get_tree().change_scene_to_file("res://scenes/arena3d.tscn"))
```
But it is structurally disconnected from the tournament path. `_ready()` (line 35-40) builds its
own standalone demo team (`Roster.monsters.slice(0, 5)`) and a synthetic scouted rival
(`Roster.make_rival_team(team_a.size(), 0.3)`) — it does not read `Career`'s active cup state at
all. And **`tactics.tscn` has zero inbound references anywhere in the live navigation graph**:
grepping every `change_scene_to_file(...)` in `scripts/ui/*.gd` for `tactics.tscn` returns
nothing except `tactics_ui.gd`'s own outbound calls. Nothing sends the player there. It is a
polished, reachable-only-by-direct-scene-load demo, not a step in the actual game.

⚠️ **This also means `docs/ACCESSIBILITY.md`'s stated scope is now stale.** That document
describes its audited path as *"the live navigation loop — title.tscn → stable.tscn →
tactics.tscn → arena3d.tscn → report.tscn."* `stable_ui.gd:174` does not go to `tactics.tscn`; it
goes to `tournament.tscn`, which is a dead end with no arena at all. Whoever next touches that
document should re-scope it against the graph as it actually is today.

### What React had, that this lost

`src/App.tsx:1977-2219`, the `battleSub` state machine for an active cup:

- **`preamble`** — states the sweep-or-nothing rule and the field *before* entry, so the player
  weighs the hard gate instead of discovering it by losing.
- **`bracket`** — live round-robin standings (`LiveStandingsCard`), pay to scout the next
  opponent at `basic`/`full` tiers, "Set Battle Orders."
- **`tactics`** — formation drag-reorder (`moveUp`), a Protect assignment, and Man Mark —
  explicitly **gated on having scouted** (`App.tsx:2150-2151`: *"Scout this match to see who you
  are facing — you cannot mark a monster you have not identified"*).
- **`fight`** — `ArenaBattle` plays the match live, result only revealed by watching it.
- Back to **`bracket`** for the next opponent, repeat, then **`announce`** — `BracketGrid`
  standings plus `MatchAnalysis`, a causal post-fight report (turning point, tactic ✓/✗,
  counter-read).

Every one of those beats is gone from the reachable Godot cup. None of the *pieces* are missing
from the codebase — `tactics_ui.gd` alone is arguably better than what it would replace (see GAIN
1 below) — they are simply not wired to the path the player actually takes.

**Recommendation:** this is a sequencing problem, not a lost-art problem. Wire
`tournament_ui.gd`'s "Enter the Cup" to loop `tactics.tscn → arena3d.tscn` per round, carrying
win/loss state between rounds the way React's `matchIdx` / `fightOutcomes` did, instead of
calling `enter_league_tournament` as one headless batch call.

## REGRESSION 2 — No healing anywhere in the Godot build

React's Market has a dedicated Infirmary panel (`App.tsx:941-959`) — pay gold to mend HP/MP
immediately instead of losing a week to Rest. Grepped `monster-tamer/scripts` for
`infirmary|heal`: the only hits are internal battle-sim mechanics (lifesteal, `hpRegenBuff`,
status math) — there is no player-facing heal action anywhere in the UI. A monster that comes
home from a lost cup at low HP has exactly one recovery path (a full week of Rest). Unlike the
Lab/Breeding placeholders, this gap is **not disclosed anywhere** in the files I read — it reads
as an oversight rather than a stated scope decision, and is worth confirming with whoever owns
the market/economy build order.

## GAIN 1 — "The Read" (`tactics_ui.gd`) is a genuine improvement on React's tactics panel

Once it is wired into the reachable graph (Regression 1's fix), this screen is better than the
one it would replace:

- A real **deployment board** (`deployment_board.gd`) replaces React's blind Tight/Loose
  dropdown — formation is now *derived* from actual drag-placement, per `docs/UX_DEPLOYMENT.md`.
- Per-monster target priority has an explicit **"Team default" inherit state**
  (`tactics_ui.gd:227`), distinct from an explicit override — React never modelled that
  distinction; a per-monster choice silently masked the team default with no way to tell.
- The rival gameplan panel states **tell / win condition / counter-read** up front
  (`tactics_ui.gd:267-280`) — richer than React's `GAMEPLANS` text, which only surfaced this late,
  behind a paid Battle Analyst.
- Man-mark selection is keyboard-accessible with a focus ring drawn **independently** of the
  "marked" gold border (`tactics_ui.gd:352-366`, `_style_rival_panel`) — React's equivalent
  interaction was mouse-only.

## GAIN 2 — Plan-then-commit weekly loop (`training_ui.gd` + `feeding_ui.gd` + `stable_ui.gd`)

New this session, well built, and it fixes a real bug the code comments document
(`training_ui.gd:1-10`: training used to apply a stat gain immediately on click, no clock, no
cost — *"i can still train infintely"*). The write-a-plan / Advance Week / narrated-result
structure mirrors React's own `WeekPlanEntry` discipline, and `stable_ui.gd`'s sticky action rail
states the week's gold+stamina bill *before* the button is pressed (`_refresh_advance_note`) —
better legibility at that exact point than React had.

## GAIN 3 — Locked-not-hidden doors, stated reasons (`town_ui.gd`)

`town_ui.gd:256-284`'s `forced_disabled`/`forced_reason` pattern — a built destination
temporarily disabled with one tooltip, vs. an unbuilt one permanently locked with a different
tooltip — is a consistent, honest affordance React never had; React simply omitted a hub button
until the feature existed. *"A visibly-not-yet-implemented door is fine; a button that lies is
not"* (the file's own words) is a good standard and it is applied consistently across all seven
`LOCATIONS` entries.

## What I did NOT find (checked, not assumed)

- **The P0 keyboard-lockout claimed by the earlier pattern-library pass is confirmed false.**
  Read `stable_ui.gd:251-269` and `tactics_ui.gd:301-349` directly: both wire
  `focus_mode = Control.FOCUS_ALL` and handle `ui_accept`/`ui_select` alongside the mouse path,
  matching `docs/ACCESSIBILITY.md`'s own withdrawal note. Not re-flagging it.
- **`UI_LAYOUT_RULES.md`'s scroll-everywhere rule is respected in every screen read this
  session.** `tournament_ui.gd`, `training_ui.gd`, `feeding_ui.gd`, `market_ui.gd`, `shop_ui.gd`,
  `lab_ui.gd`, `breeding_ui.gd`, `stable_ui.gd`, and `town_ui.gd` all wrap body content in a
  `ScrollContainer` with the primary action pinned outside it. No new clipping regressions found.

Four of four dramatic agent findings produced earlier today were false when checked against the
implementation. This section is deliberately kept as prominent as the defect list above — stating
plainly what was verified as fine is exactly the discipline this project's `CLAUDE.md` keeps
asking for, and it is cheap to lose track of once an audit starts finding real problems.
